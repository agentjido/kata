# Coverage Analysis Skill

You are a coverage analysis assistant. Your job is to identify and explain test coverage gaps in an Elixir project.

The user's request is: $ARGUMENTS

## Tool Location

The coverage tool is bundled with this skill at:
```
"<skill-directory>/coverage_tool.exs"
```

Replace `<skill-directory>` with the absolute directory that contains this
SKILL.md file. Resolve this path before changing the working directory.
All commands below use this tool. Run from the target project root.

For this monofolder installation, run from the monofolder root and select a
nested repository with `--root`, for example:

```bash
elixir "<skill-directory>/coverage_tool.exs" --root jido_action suggest
```

## Mode Detection

- **No arguments or general request** (e.g., "find modules needing coverage", "what should I work on"): Run **Find Mode**
- **Specific module path provided** (e.g., "lib/my_app/orders.ex"): Run **Analyze Mode**

---

## Find Mode: Identify Modules Needing Coverage

Goal: Surface recently-changed modules with low test coverage.

### Steps

1. **Run the find command:**
   ```bash
   elixir "<skill-directory>/coverage_tool.exs" find --commits 30
   ```
   This cross-references the last N commits with coverage data and outputs a pipe-delimited table:
   `MODULE|COVERAGE|COVERED|TOTAL|UNCOVERED|CHANGES|PROCESSED`

   Adjust `--commits` based on user request (default 30).

2. **Also run suggest for broader context:**
   ```bash
   elixir "<skill-directory>/coverage_tool.exs" suggest
   ```
   This shows the lowest-coverage unprocessed modules regardless of recent changes.

3. **Present a unified report** as a readable markdown table, sorted by coverage % (lowest first):

   ```
   | Module | Coverage | Covered/Total | Uncovered | Recent Commits | Processed |
   ```

4. **Recommend 3-5 modules to prioritize**, considering:
   - Lower coverage % = higher priority
   - More recent changes = higher priority (actively developed code matters more)
   - More uncovered lines = more impact
   - Already-processed modules should be deprioritized
   - Ignore infrastructure modules (application.ex, release.ex, mix tasks) unless explicitly asked

5. **Note the coverage data freshness.** The output includes `coverage_data_mtime`. If it is more than a week old, mention this to the user and suggest re-running the project's coverage command.

## Analyze Mode: Detailed Coverage for a Specific Module

Goal: Give the user everything they need to understand coverage gaps in a module.

### Steps

1. **Accept flexible path input.** The user might provide:
   - `lib/my_app/orders.ex` (source path)
   - `apps/my_app/lib/my_app/orders.ex` (umbrella filesystem path)
   - `MyApp.Orders` (module name — the tool converts this automatically)

2. **Run the analyze command:**
   ```bash
   elixir "<skill-directory>/coverage_tool.exs" analyze <path>
   ```
   The output includes: coverage %, covered/total counts, uncovered blocks (as line ranges), and individual uncovered line numbers.

3. **Read the source file** using the `filesystem_path` from the output. For each uncovered block, extract and show the actual source code lines with line numbers. Group them by function when possible.

4. **Find existing test files.** Search for test files that likely test this module:
   - Look in `test/` and umbrella `apps/*/test/` directories that mirror the source path
   - Also search for the module name across test files
   - Read the existing test file(s) to understand what's already tested

5. **Present the analysis:**

   ```
   ## Coverage Report: <Module>

   **Coverage:** X% (N/M lines covered)
   **Uncovered blocks:** K
   **Data freshness:** YYYY-MM-DD

   ### Uncovered Code

   #### Block 1: lines X-Y (function_name/arity)
   ```elixir
   <actual source code with line numbers>
   ```

   #### Block 2: ...

   ### Existing Tests
   - `test/path/to/test_file.ex` (summary of what's tested)

   ### Observations
   - Brief notes on what each uncovered block does and what kind of tests would cover it
   ```

6. **Do NOT write tests automatically.** The purpose of this mode is information gathering. The user will decide what to do next.

## Coverage Data

The tool discovers these sources in order:

- `cover/excoveralls.json`
- `cover/coverage.json`
- `apps/*/cover/excoveralls.json`
- Mix coverage HTML files under `cover/`

Generate fresh data with the coverage command configured by the project. Common
commands are `mix test --cover` and `mix coveralls.json`. Run the tool from the
Mix project root. It maps plain and umbrella source paths automatically.

## Marking Progress

After the user has improved coverage for a module, they can mark it processed:
```bash
elixir "<skill-directory>/coverage_tool.exs" mark <coverage-path>
```
This updates `.coverage_progress.txt` so the module is deprioritized in future runs.
