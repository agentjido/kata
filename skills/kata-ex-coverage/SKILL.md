# Coverage Analysis Skill

**Outcome:** A coverage-gap report that lets the project maintainer select the
next Elixir test target or understand one module's uncovered behavior.

**Done:** The requested mode reports exact figures from current coverage data,
the relevant source and test evidence, data freshness, and analysis limits, or
states the specific data or module blocker. Project source remains unchanged.

## Assignment

The required input is one Elixir project with generated coverage data. A module
path or module name selects Analyze mode; otherwise use Find mode. The practice
is test-coverage analysis. The work profile is `bounded-execution`.

Direct user authority or inherited caller authority permits reading the target
project and running the bundled analyzer. Do not write tests, change source,
install tools, or generate new coverage data unless the operator asks. Change
`.coverage_progress.txt` only after an explicit request to mark completed work.
Do not change remote state. If coverage data is missing or unusable, report the
required generation command from the target project instead of guessing.

## Resolve the analyzer

The analyzer is `coverage_tool.exs` beside this file. Resolve
`<skill-directory>` to this skill's absolute directory before changing the
working directory. Run the command from the target Mix project root:

```sh
elixir "<skill-directory>/coverage_tool.exs" <command>
```

For a workspace that contains several projects, select one with `--root`:

```sh
elixir "<skill-directory>/coverage_tool.exs" --root <project> suggest
```

The tool checks `cover/excoveralls.json`, `cover/coverage.json`, umbrella-app
ExCoveralls JSON, then Mix coverage HTML. The target project's configured
coverage command is authoritative. Common commands are `mix test --cover` and
`mix coveralls.json`.

## Find weak modules

Use this mode when the request does not name one module.

```sh
elixir "<skill-directory>/coverage_tool.exs" find --commits 30
elixir "<skill-directory>/coverage_tool.exs" suggest
```

Change the commit count only when the request or repository activity supports a
different window. Combine the results in one table, sorted from lowest coverage:

```text
| Module | Coverage | Covered/Total | Uncovered | Recent Commits | Processed |
```

Recommend three to five modules when that many valid candidates exist. Rank by
low coverage, recent changes, and uncovered-line impact. Deprioritize processed
modules. Exclude infrastructure modules unless the operator asks about them.
Report `coverage_data_mtime`; when it is more than one week old, state that the
maintainer must refresh coverage before using the report for a current decision.

## Analyze one module

Accept a source path, umbrella path, or Elixir module name. Run:

```sh
elixir "<skill-directory>/coverage_tool.exs" analyze <module-or-path>
```

Use `filesystem_path` from the output. Read each uncovered block with line
numbers and group it by function when the source supports that grouping. Find
tests through mirrored `test/` or `apps/*/test/` paths and a search for the
module name. Read the relevant tests before you describe what is missing.

Report the module, exact coverage and covered/total counts, data freshness,
uncovered blocks with source lines, existing test paths and behavior, and short
observations about the behavior a future test must exercise. Do not write the
tests.

## Mark completed work

Only after the operator says coverage work is complete, run:

```sh
elixir "<skill-directory>/coverage_tool.exs" mark <coverage-path>
```

This updates `.coverage_progress.txt` and affects later suggestions.

## Verify and report

Check that analyzer output contains the expected result marker, figures, module
path, and freshness field for the selected mode. Check that cited source and
test paths exist. Confirm that source and tests did not change. Report the mode,
commands, data source and freshness, findings, any progress-file change, and
each unresolved limit.
